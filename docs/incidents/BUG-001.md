# BUG-001 — Estoque alterado após pedido recusado

## Resumo do defeito

Um pedido com dois produtos é recusado porque um deles não possui estoque suficiente. Mesmo sem criar
o pedido, a aplicação reduz o estoque do outro produto.

| Campo | Valor |
|---|---|
| Status | Aberto |
| Severidade | Crítica |
| Prioridade | P0 |
| Ambiente | Local — `http://localhost:8080` |
| Frequência | Reproduzível |

## Cenário

- Produto A: ativo, estoque `10`, quantidade solicitada `2`.
- Produto B: ativo, estoque `1`, quantidade solicitada `2`.
- O produto A deve ser cadastrado antes do produto B.

O produto B não consegue atender ao pedido. Portanto, o pedido inteiro deve ser recusado sem modificar
nenhum estoque.

## Preparação

1. Inicie a aplicação em `http://localhost:8080`.
2. Obtenha um token de administrador:

```http
POST /api/v1/auth/login
Content-Type: application/json
```

```json
{
  "email": "admin@orderflow.local",
  "password": "LocalAdmin123!"
}
```

3. Copie o campo `accessToken` da resposta e use-o como `Bearer <accessToken>` nos próximos pedidos.
4. Crie uma categoria:

```http
POST /api/v1/categories
Authorization: Bearer <accessToken>
Content-Type: application/json
```

```json
{ "name": "BUG-001 QA" }
```

5. Copie o `id` retornado como `<categoryId>` e crie o produto A:

```http
POST /api/v1/products
Authorization: Bearer <accessToken>
Content-Type: application/json
```

```json
{
  "categoryId": <categoryId>,
  "name": "Produto A BUG-001",
  "sku": "BUG001-A-<timestamp>",
  "price": 10.00,
  "stock": 10
}
```

6. Crie o produto B com o mesmo `categoryId`, outro SKU e `stock` igual a `1`:

```json
{
  "categoryId": <categoryId>,
  "name": "Produto B BUG-001",
  "sku": "BUG001-B-<timestamp>",
  "price": 20.00,
  "stock": 1
}
```

7. Anote os dois `id` retornados. O primeiro é o produto A e o segundo é o produto B. Não use os
   números `101` e `102` literalmente; eles são apenas exemplos.

## Passos para reproduzir

1. Envie a requisição abaixo, substituindo `<productAId>` e `<productBId>` pelos identificadores reais:

```http
POST /api/v1/orders
Authorization: Bearer <accessToken>
Idempotency-Key: bug-001
Content-Type: application/json
```

```json
{
  "shippingAddress": "Rua das Flores, 100",
  "items": [
    { "productId": <productAId>, "quantity": 2 },
    { "productId": <productBId>, "quantity": 2 }
  ]
}
```

2. Confirme que a API recusou o pedido.
3. Consulte `GET /api/v1/orders` e confirme que nenhum pedido foi criado.
4. Consulte `GET /api/v1/products?size=100` e confira os estoques de A e B.

### O que comparar

Antes de enviar o pedido, A deve mostrar `stock: 10` e B deve mostrar `stock: 1`. Depois da resposta
de recusa, os mesmos valores devem continuar iguais. O único resultado esperado da tentativa é a
recusa do pedido.

## Resultado encontrado pelo QA

| Produto | Antes da tentativa | Depois da tentativa |
|---|---:|---:|
| A | 10 | 8 |
| B | 1 | 1 |

- Resposta do pedido: `409`.
- Pedido criado: não.
- Defeito: o produto A perdeu duas unidades sem existir um pedido correspondente.

## Resultado esperado

- A API recusa o pedido.
- Nenhum pedido é criado.
- O estoque de A permanece `10`.
- O estoque de B permanece `1`.

## Impacto

O catálogo pode indicar indisponibilidade de produtos que não foram vendidos. Isso pode bloquear novas
compras e exigir correção manual do estoque.

## Critérios de aceite

- O cenário descrito mantém os dois estoques inalterados.
- Nenhum pedido é persistido após a recusa.
- A resposta de erro continua segura e coerente com o contrato atual.
- Um pedido válido continua reduzindo o estoque normalmente.
- Existe um teste automatizado cobrindo o cenário do defeito.
- A suíte relevante permanece aprovada.
